# Working rules (from the user)

- Work **feature by feature** (screen by screen with its own db components). Do not fix or refactor anything outside
  the feature asked for; no long unrequested work. Mention other issues briefly instead of fixing them.
- Before changing a feature, check `apex/ARCHITECTURE.md` for its dependencies in both directions
  (what it uses and what uses it), and keep that file up to date when a feature changes.
- Deliver each feature as a small deployable patch: `apex/patches/NN-<feature>/` + zip (db script, changed app
  files under `app/`, README with deploy steps), on top of the latest release.
- Do not guess table or column names (ask for DDL); keep component IDs unless a fix needs a change.
- UI: Universal Theme with the **Redwood Light** theme style only (users cannot switch styles); use its standard templates.
- Rules: OOTB APEX first; access/admin changes from the application console; every page has 2+ privileges
  (View/Create/Manage) plus data security; reusable patterns; deploy in chunks.
- Test only what the feature touches (its db test + browser test).
- Layout: everything APEX lives under `apex/`, which is the SQLcl project root (`apex/.dbtools/`,
  `apex/src/database/xxcus/...`, `apex/dist/`); the APEX app is `apex/src/database/xxcus/apex_apps/f134`; `apex/db` holds the idempotent install/upgrade scripts (source of truth for DB).
- Database: one APEX workspace (XXCUS). XXCUS is the workspace's default (primary) schema and the parsing schema
  of the business apps (KYC = app 134); **XXFUSION** is the schema for Fusion web-service data and the COMMON
  application (shared security, setup, workflow), source `apex/src/database/xxfusion/apex_apps/f135`.
- **Golden rule: work only in `repos/` (from the user, release 106 onwards).** Every change from now on is made in
  the relevant folder of `repos/` only - `repos/common/` (COMMON, app 135) or `repos/kyc/` (KYC, app 134) - never in
  `apex/`, which is frozen as history. Do not run `repos/tools/build_repos.py` again (it would overwrite `repos/` from
  `apex/`). The uploadable version of each release (the importable APEXlang zip and its patch) is kept in git in that
  application's own folder (`repos/<app>/releases/`). No database is started or run: changes are validated offline
  with the Oracle skills (Db and Apex skills, APEXlang validation). Live validation is done by the user's server
  through the web (browser) tool when the user gives access, signed in as a set of test users (one per role and
  privilege level, per application), kept as a script in `repos/<app>/db/admin/` - prepare that set before live tests.
- **Reference documents (from the user):** each application's documentation lives in git under `repos/<app>/docs/`:
  `README.md` is the requirements summary (synced to the GitHub Project README by `docs-sync.yml`), and
  `components/<component>/` (one folder per `features/<component>`) holds `requirements.md` (functional requirements -
  read first and updated in the same PR as the code; `docs-check.yml` warns otherwise, "no-req-change" in the PR body
  skips it), `technical.md` (generated by `repos/common/tools/feature_docs.py` on every build), and the training material
  produced later from browser screen recordings: `user-guide.md`, `training-manual.md`, `setup-manual.md`, `video.md`
  (link to the video, a GitHub Release asset - no mp4 in git), `narration.md` (voice-over script) and `subtitles.vtt`.
  The claude.ai requirements page (https://claude.ai/artifact/AkQYLkw1WPgmCH1d8b8z9G) is no longer updated.
- **Claude codes and reviews, the git workflow does the rest (from the user, 2 Nov 2026).** Claude only changes the
  code and reviews it offline, then opens the PR and pushes; deployment, database checks, tests, release zip, merge
  and error reports are done by the COMMON pipeline (`repos/common/deployment/README.md`). GitHub settings still to do
  by the user: `repos/common/deployment/GITHUB-SETUP.md`.
- **PR and run naming (from the user, 3 Nov 2026, issue #218).** PR title `<APP> Release <Number>: <short summary>`
  (summary at most 60 characters); every issue of the release is linked in the PR body with `Fixes #n` (never listed in
  the title). Claude squashes its local work into one commit per push; each push is one pipeline run named
  `<PR title>: Push Number <N>`, with all its jobs inside. Fix and review locally, then push once.
- **Netlify not used for now (from the user, 2 Nov 2026).** Netlify stays connected for later use, but nothing is
  deployed, published or triggered there now; `netlify.toml` keeps every build skipped (`ignore = "exit 0"`) - do not
  change it until the user asks. Pushing to the session branch is allowed; a PR merges only through the COMMON pipeline
  (required check "9 Finalize the PR" + GitHub auto-merge, `repos/common/deployment/README.md`).
- **Issue backlog (from the user):** the backlog is the GitHub issues of this repository, shown on two GitHub Projects:
  "KYC Application" (https://github.com/users/mazharr-hussain/projects/3, label `KYC`) and "Common Application"
  (https://github.com/users/mazharr-hussain/projects/4, label `COMMON`); the workflow `add-to-project.yml` puts each
  labelled issue on its board. Every issue reported (or found) becomes a GitHub issue at once, before any plan, with its
  one label only (`KYC` / `COMMON`), its I-number in the title, and in its body the lines `Type: Bug|Enhancement|Task`
  and `Priority: P1|P2|P3` - the workflow copies them into the project fields "Issue Type" and "Priority". A release PR closes its issues with "Fixes #n" in the PR body,
  so they close (Done on the board) when the PR merges. `repos/ISSUES.md` mirrors the list (I-number -> issue number,
  fixed release). Read the open issues at the start of every chat and show the closed / still-open issues after each release.
- **Golden rule: issues, then plan, then approval.** Collect all the issues the user reports first; when the user
  confirms the list is complete, propose a plan; start nothing without the user's approval of that plan.
- **Golden rule: no install error, ever (no ORA-00955).** Base table scripts (01-04) create a table, with its indexes
  and comments, only when it is missing (`XXFND_DDL_PKG.CREATE_TABLE`); an existing table is left as it is. Every
  change to an existing object is a checked step in a later numbered script (`XXFND_DDL_PKG.ADD_COLUMN`,
  `DROP_COLUMN`, `ADD_CONSTRAINT`, `DROP_CONSTRAINT`, `ENSURE_INDEX`, `DROP_INDEX`, `ENSURE_SEQUENCE`), listed for
  install and upgrade, so every database gets exactly what it is missing and a re-run does nothing. Never edit a base
  CREATE to change an existing table. Test every release with a fresh install, an install over existing objects,
  an upgrade, a re-run, and the App Builder import screen.
- **Golden rule: one package per component, business logic in its own place.** Each component has its own package
  (request logic in the request package, case logic in the case package, party logic in the party package, and so on);
  a component never holds another component's logic. When one component needs another's logic, it calls that
  component's procedure / function - never a copy - so each rule lives in one place and is shared. Logic common to
  every component (e.g. workflow start / end / state, the RFI workflow and its loop, tasks, notifications) lives once in
  COMMON; what is specific to a component (its screens, its validations, invoking the common workflow, its own rules)
  stays in that component's package. Keep shared things common to avoid duplication, and component things separate
  for better management. Changes to this structure still follow the issues, plan and approval rule.
- **Golden rule: no HTML in PL/SQL.** Build the UI with APEX components (classic / interactive reports, cards,
  template components, forms, display items, standard region templates) fed by SQL; packages return data, not markup.
  HTML is generated in PL/SQL only when no APEX component can do the job, and then the reason is written in a comment
  next to it.
- **COMMON first:** the KYC freeze (until COMMON was finished) ended with release 68 (approved plan: clean script,
  COMMON screens, data move, KYC uses COMMON). Shared setup screens live in COMMON only; KYC links to them
  (XXFND_ADMIN_SCOPE_PKG.SETUP_PAGE_URL). Build one app with `python3 apex/tools/build.py --release N --app COMMON`.
- **Golden rule: COMMON components are never duplicated (from the user).** No application copies a COMMON component
  (screen, package logic, LOV, authorization, workflow, task, setup). An issue in COMMON is not fixed in COMMON from an
  application release and not worked around with a copy: it is listed for the COMMON team in `apex/COMMON-ISSUES.md`
  with its details. Even if the user asks to duplicate a COMMON component in future, it must be reconfirmed with the
  user three times before anything is done.
- **Golden rule: data in COMMON changes only through COMMON routines (from the user).** An application never changes
  COMMON data (XXFND_ tables) with a direct database command (INSERT, UPDATE, DELETE, MERGE); it calls the COMMON
  routine for it. Where no routine exists, the gap is listed for the COMMON team in `apex/COMMON-ISSUES.md` - never
  worked around with direct SQL. Every COMMON routine that changes data has a parameter for the application (its code
  or ID) and changes only that application's rows (another application's rows are refused); applications are granted
  SELECT, EXECUTE and REFERENCES (for foreign keys to COMMON keys) on COMMON objects only, never INSERT, UPDATE or DELETE.
- **Golden rule: who sees COMMON data (from the user).** Setup data (lookups, flexfields, document categories,
  attachment pages, approval rules, templates, roles, menu entries, ...) is visible per application: an application and
  its administrators see the setup rows that belong to that application (plus COMMON's shared ones); IT sees all.
  Transaction data (tasks, notifications, documents, information requests, e-mails, ...) is visible per user: each user
  sees what they are allowed to see, from any application (e.g. My Tasks shows their tasks of every application).
- **COMMON scope only (from the user):** a component that belongs to COMMON lives only in COMMON scope; KYC (and every
  other application) uses it as it is - no change, no redevelopment, no duplication.
- **COMMON is completed on its own (from the user):** KYC and COMMON are two different applications. For now treat KYC
  as if it did not exist: no KYC work, no KYC dependency in COMMON's design or tests. COMMON is finished first as a
  standalone application; the user makes all KYC changes later in one go, on the completed COMMON.
- **Always use the Oracle skills** for database and APEX work: the Db and Apex skills from
  `mazharr-hussain/OracleskillsMirror` (clone to `/home/user/mazharr-hussain/oracleskillsmirror`, fetch the latest first;
  `db/SKILL.md`, `apex/apexlang/26.1/`). Read the matching skill file before reviewing or changing DB objects or APEXlang.
- **No database in the chat session (from the user):** reviews and changes are validated offline against the files
  (`repos/<app>/db`, the APEXlang source, the Oracle skills); the database checks run in the COMMON pipeline on the
  validation database (fresh install, upgrade with data, online validation, DB tests).
