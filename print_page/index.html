    Version 2 — Business Process Guide¶

    How We Work Today: The As-Is KYC Process¶

    Document Type: Business Process Guide
    Audience: Compliance Team, Management
    Source: Requirements Gathering Session — Head of Enterprise Risk & Compliance
    Status: Current manual process — basis for all future improvements

    This document faithfully captures how the compliance team currently operates — including every manual step, every tool used, and every known difficulty. It is not a criticism; it is an honest baseline from which to improve.

    Overview¶

    Today, the KYC process at Qatari Diar is a mostly manual process. The existing KYC Report Application (a JSF-based web system) is used only at the end: the officer enters the completed report data and the system manages the approval workflow and record storage. Everything before that — receiving requests, collecting documents, conducting due diligence, and compiling the full report — is done entirely outside the system through email, Excel, WorldCheck, and personal judgment. The system never sees the work; it only sees the finished output.

    This creates real risks: inconsistency between departments, reliance on personal memory, difficulty onboarding new staff, and no reliable way to answer basic management questions like "how many KYC reports did we complete this quarter?" without first requesting a data export.

    Single source of truth

    Maintained in draw.io. See the As-Is Process diagram page for all 9 pages, or edit directly at docs/diagrams/drawio/asis-process.drawio.

    Key Point

    The process only enters the KYC Report Application once all manual work is complete — documents validated, due diligence researched, entity data ready. Everything before that point is invisible to the system.

    Complete As-Is Process — One Page¶

    Who Is Involved¶

    Person Role Tools Used
    Business Department (e.g., Procurement, Sales, Egypt office) Identifies the need, runs initial check, submits documents Excel Risk Calculator, Email
    Compliance Officer (Hessa, Latifa, and others) Validates documents, conducts research, creates reports WorldCheck, KYC System, Local folders, Email
    Compliance Manager / Head (Carlos) Assigns work, manages pipeline, approves reports Email, KYC System, Excel
    System Administrator Manages user accounts and reference data inside the KYC Report Application only — has no role in the manual intake, document collection, or due diligence work upstream KYC System

    Phase 0: Deciding Whether a KYC is Needed¶

    Who does this: The business department that wants to engage a new counterparty

    Before the compliance team is even involved, the requesting department runs a check using an Excel-based Risk Calculator. This spreadsheet was built to match QD's internal KYC policy and asks a series of questions about the counterparty:

    • Who are they? (a company or an individual)
    • Where are they from? (Qatari, majority-Qatari, minority-Qatari, foreign)
    • What type of relationship does QD plan to have with them? (supplier, buyer, tenant, investor, etc.)
    • Is there any financial involvement, current or proposed?
    • Are there any known connections to related parties?

    Based on the answers, the Excel says either "KYC Required" or "KYC Not Required".

    What goes wrong here

    • Different departments send requests in completely different formats — there is no standard
    • When KYC is not required, the Excel output is saved locally but there is no formal evidence record that the check was done
    • The Excel can be changed manually, so the output depends on the honesty and judgment of the person filling it in

    Phase 1: Receiving and Validating Documents¶

    Who does this: Compliance Officer

    The compliance team receives an email in their shared mailbox. The email contains the Risk Calculator and attached documents. The officer opens everything and checks whether the documentation is sufficient to conduct proper due diligence.

    What "sufficient" means:

    For an individual person: A government-issued photo ID (Qatar ID or passport) is generally enough.

    For a company: The officer needs an official document that shows — clearly and completely — who owns the company and who controls it. In Qatar, a Commercial Registration (CR) usually does this. In other countries (Egypt, UK, Tajikistan), different documents serve this purpose — so there is no single fixed checklist.

    What the officer is always looking for is: "Can I trace the ownership all the way to a real person?"

    What goes wrong here: - Everything is tracked in email threads — there is no system record of how many rounds of back-and-forth happened - Documents are saved to the officer's local workstation. At the end of the day, they must be manually moved to a QDocs folder — but there is no check for whether a folder for that entity already exists, and no standard naming convention - New staff (e.g., Hessa) have no way to know if a report has been done before for the same entity. Institutional knowledge lives only in people's memories

    Phase 2: Assigning the Work¶

    Who does this: Compliance Manager

    The manager looks at who is available (not on leave, not overloaded) and assigns the case to a compliance officer. This is done verbally or by email — there is no assignment record in the system.

    What goes wrong here: - Assignment happens outside the system — there is no record of when or to whom a case was assigned - The manager has no workload view; they must ask each officer individually how many active cases they have - If the manager is absent, there is no way for the team to know how work should be prioritised or distributed

    Phase 3: Conducting the Due Diligence (WorldCheck)¶

    Who does this: Compliance Officer

    Once assigned, the officer opens WorldCheck — an external international database — in their web browser. This is a separate tool, entirely disconnected from the KYC system.

    For each entity and each significant individual (UBO), the officer: 1. Searches by name 2. Reviews the results for matches 3. Determines whether a match is genuine or a false positive 4. Notes whether the entity or person is a PEP (Politically Exposed Person) — for example, a state-owned company is connected to the government, which counts as a PEP link 5. Looks at shareholders and connected entities

    What goes wrong here: - There is no structured way to record what was found — it goes into a free-text field in the system later - There is no record of when the screening was done or which databases were checked - The officer carries the findings in their head until they sit down to enter them into the system

    Phase 4: Recording the Entity in the System¶

    Who does this: Compliance Officer

    The officer logs into the KYC system and creates an Entity record for the counterparty, entering all the details from their research. For companies, they add each UBO and authorised signatory as a separate sub-record.

    What goes wrong here: - The system does not check whether this entity was already recorded before. If the same company was screened six months ago, the officer won't know unless they remember or happen to search - Screening results go into a single free-text box — there is no structure for recording the date, the source, whether it was a match or not, or whether the person is a PEP - Date fields (like date of birth) accept any text — the system will happily accept "12-0-2024" or "32/13/2025" without warning

    Phase 5: Creating the KYC Report¶

    Who does this: Compliance Officer

    Next, the officer creates the formal KYC report in the system. This involves entering many fields that could theoretically be pre-filled from the entity record — but the system requires re-entering them from scratch.

    One particular pain point: the final conclusion. Around 95% of the time, the conclusion follows a standard template. But those templates are stored in Word documents on shared drives, not in the system. The officer opens Word, copies the relevant template, pastes it into the system, and adjusts it.

    What goes wrong here: - The request date field has no validation — an officer under pressure might inadvertently enter a wrong year and not notice - The system does not warn when the entered date does not match the actual chronology of events - Documents must be uploaded from the local workstation — they cannot be linked from QDocs

    Phase 6: Level 1 Approval¶

    Who does this: Level 1 Approver (currently Latifa)

    Where this happens: Inside the KYC Report Application (the existing JSF system). The approver logs into the application and sees the submitted report in their approval queue.

    The approver reviews the full report, reads the conclusion, checks the attached documents, and then acts directly in the application:

    • Approve — satisfied with the work; status moves to Approved (L1)
    • Request For Information (RFI) — something is unclear; sends the report back to the officer with a comment recorded in the application
    • Reject — the report is closed with a stated reason recorded in the application

    Approval routing by risk (handled by the application): - Low risk → Level 1 approval is the final approval — report status moves to Final Approved - Medium or High risk → report automatically routes to Level 2 queue

    Four-eyes control — already enforced today: The application blocks a user from approving a report they created themselves (contributor and approver must be different accounts). This one control does work reliably in the current system; it is not one of the gaps this document raises.

    What goes wrong here: - If the Level 1 Approver is unavailable (on leave, travel), a substitute must be manually arranged by phone or email — the system has no delegation mechanism - There is no way in the system to see how many reports are waiting for approval at any given time

    Phase 7: Level 2 Approval (Medium/High Risk Only)¶

    Who does this: Level 2 Approver / Head of Compliance (Carlos)

    Where this happens: Inside the KYC Report Application — the report appears in Carlos's queue after L1 approval.

    Same actions as Level 1 — full review inside the application, then Approve / RFI / Reject. Once approved at Level 2, the report status is set to Final Approved in the application.

    What goes wrong here: - If the Level 2 Approver (Carlos) is unavailable, a substitute must be manually activated by phone — the system has no delegation or deputy mechanism - There is no mandatory checkpoint for Suspicious Activity Reports (SARs) — the question of whether a SAR should be filed is not formally built into the approval step

    What should happen but doesn't:
    The requesting department should automatically receive the completed report and a notification that the KYC is done. Currently, this does not happen — someone on the compliance team has to remember to email them.

    Phase 8: Reporting and Tracking¶

    Current reality:

    There is no live dashboard. When management needs to know: - How many KYCs were completed this month? - How long is our average turnaround time? - Which cases are overdue?

    The answer is always: "Madi, send me an export." A data extract is requested, downloaded to Excel, and manually analysed.

    Additionally, there is no system to flag when a previously approved KYC is due for periodic review. This is managed — imperfectly — by memory and the manager's judgment.

    Process Status Labels (Current)¶

    The compliance team informally categorises their pipeline using these statuses — some are in the system, some exist only in email folder labels:

    Status Where It Lives Meaning
    In Progress Email / memory Officer actively working on it
    Waiting for More Information Email flag Documents requested from department
    Waiting for Approval KYC System Report submitted, in approver's queue
    Draft KYC System Saved but not yet submitted
    Submitted KYC System Sent to Level 1
    Approved (L1) KYC System Passed Level 1 review
    Approved (Final) KYC System All approvals complete
    Rejected KYC System Closed — not proceeding
    RFI KYC System Information requested by approver

    Summary of Known Problems¶

    Problem Consequence
    No standard intake form — requests arrive by email in any format Officers spend time decoding inconsistent submissions
    Documents saved locally, moved manually to QDocs Risk of loss, no naming standard, no institutional memory
    No duplicate entity detection Same company screened multiple times with no link
    Screening results are free text with no structure Cannot audit what was checked or when
    Date fields accept invalid values KPI data is unreliable
    Conclusion writing requires external Word document Slow, inconsistent, error-prone
    No approver delegation Approvals stall when approver is absent
    No completion notification Requestors don't know when KYC is done
    No live KPI reporting Management can only view data through manual exports
    System has no source code If it breaks, it cannot be fixed — urgent risk

    V3 — Best Practice Process Guide¶

    Compliance Standards

    This process is aligned to FATF 40 Recommendations, Basel KYC Guidelines, EU 6AMLD, and ISO 31000.

    Version 3 — Business Process Guide¶

    Best Practice KYC Process¶

    Document Type: Business Process Guide
    Audience: Compliance Team, Management, Internal Auditors, Regulators
    Standards: FATF 40 Recommendations | Basel KYC | EU 6AMLD (as benchmark) | ISO 31000
    Note on EU 6AMLD: The Sixth Anti-Money Laundering Directive is an EU instrument. It is referenced here as an international best-practice benchmark, not as a binding regulatory obligation. Qatari Diar applies these standards where they represent the current global compliance standard and where they govern relationships with European counterparties or subsidiaries.
    Status: Target operating model — design for next-generation system

    Why This Redesign?¶

    The requirements gathering session identified that the current process relies too heavily on individual memory, email threads, and personal judgment. This creates inconsistency, audit gaps, and significant operational risk.

    This redesigned process achieves four things: 1. Replaces manual steps with system-enforced controls wherever the decision is rule-based 2. Preserves human judgment for the steps that genuinely require expertise 3. Creates a complete evidence trail that satisfies regulatory examination 4. Gives management visibility without needing to request data extracts

    The Seven Principles This Process Upholds¶

    Every step in this process is designed around seven core compliance principles:

    1. Know Who You Are Dealing With — Identity verified, ownership traced
    2. Assess the Risk — Risk level determined systematically, not just by feel
    3. Match the Effort to the Risk — More scrutiny for higher-risk counterparties
    4. Two Pairs of Eyes — No single person approves their own work
    5. Leave a Trail — Every action documented, timestamped, and attributable
    6. Protect the Evidence — Documents stored properly, not on someone's laptop
    7. Keep It Current — KYCs reviewed regularly, not just once

    The Improved Process: Phase by Phase¶

    Phase 0: Standardised Digital Intake¶

    What changes: Business departments no longer send emails in any format they like. Instead, they complete a structured digital intake form in the system.

    How it works:

    Single source of truth

    See the Intake & Document Validation diagram — maintained in draw.io, edited visually at diagrams.net, renders automatically here and there.

    What this fixes: - Every request is in the same format, regardless of which department sends it - When KYC is not required, there is a permanent evidence record — not just a forgotten email - The documents are attached to the case from the very beginning — no local folders

    Phase 1: Document Validation — System-Assisted¶

    What changes: The compliance team uses a structured checklist rather than relying on experience and memory. The system tracks how many rounds of document requests happen. See the diagram above — the same intake-flow diagram covers both Phase 0 (intake) and Phase 1 (document validation).

    The KPI start point is the moment the compliance team confirms they have everything they need. Turnaround time is measured from here — not from the first email the department sent — because the compliance team cannot be held accountable for the department's delay in providing documents.

    Duplicate check:
    When the officer is about to create an entity, the system automatically searches for similar names. If the same company was screened before, the officer is shown the previous record and can choose to link to it, rather than creating a duplicate.

    Phase 2: Risk Pre-Assessment¶

    What is new: Before the compliance officer begins their research, the system shows them a risk indicator panel — a summary of automated risk signals computed from the data already provided.

    This does not replace the officer's judgment — it gives them a structured starting point and ensures that obvious risk factors are never overlooked.

    Risk determines the path: - Low risk → Simplified KYC (one approval required) - Medium risk → AdHoc KYC (two approvals required) - High risk → Enhanced KYC (two approvals + mandatory additional fields)

    KYC Type naming: The system uses three KYC types — Simplified, AdHoc, and Enhanced — consistently across all versions of this documentation (V2 through V6). These map directly to Low/Medium/High risk respectively, though a Confirmed Match or PEP flag can force Enhanced regardless of the initial risk level (see Phase 3).

    Phase 3: Due Diligence Research — Structured Evidence Recording¶

    What changes: The screening itself continues to be conducted manually using WorldCheck (or equivalent databases). The change is in how results are recorded in the system.

    Instead of a free-text box, the officer completes structured fields for each entity and each UBO:

    What is recorded Example
    Date screening was performed 15 June 2025
    Which database(s) were checked WorldCheck (Refinitiv)
    Reference number from screening tool WC-2025-123456
    Match status Potential Match / No Match / Confirmed Match / False Positive
    PEP flag Yes / No
    Adverse media flag Yes / No
    Findings narrative Free text — what was found
    Resolution note If false positive: why it was dismissed

    Why this matters: If a regulator asks "when did you last screen ABC Company, and what did you find?", the answer is in the record — not in someone's email archive.

    Escalation rule: If a confirmed match or PEP flag is recorded, the system automatically activates Enhanced Due Diligence requirements, regardless of what was initially selected. This overrides the risk level shown in Phase 2 — a case that was pre-assessed as Low risk is force-upgraded to Enhanced KYC type and therefore always routes through both Level 1 and Level 2 / MLRO approval. A Confirmed Match or PEP flag can never result in a single-approval, Level-1-only outcome.

    Phase 4 & 5: Entity and Report Creation — No Duplicate Entry¶

    What changes: When the officer creates a KYC report after creating the entity, the system automatically copies across the data that was already entered. The officer verifies and enriches — they do not retype.

    New mandatory fields for Enhanced KYC: - Source of funds — where does the counterparty's money come from? - Source of wealth — how did they accumulate their assets?

    These are required by international standards for high-risk counterparties and cannot be skipped when Enhanced KYC is selected.

    Conclusion templates in the system:
    Standard conclusion texts are stored in the system by risk category. The officer selects the appropriate template, which appears pre-filled in the conclusion field, ready to be personalised. No more opening Word documents.

    Date validation:
    The system will not accept: - Future dates in any date field - Invalid day/month combinations (no 32nd of the 13th month) - Request dates more than 2 years in the past (flags a warning)

    SLA indicator:
    Every report shows a traffic-light indicator: how many days have elapsed versus the target completion time for that report type.

    KYC Type Target Completion
    Simplified 5 business days
    AdHoc 10 business days
    Enhanced 20 business days

    Note on these targets: The day-counts above are proposed operational targets for the To-Be system, pending formal sign-off from Compliance management. The current As-Is process has no turnaround-time tracking (see V2, Phase 8), so no historical baseline exists to derive these from — they should be validated against actual case data once the system is live and revised if needed.

    Phase 6: Level 1 Approval — With Delegation¶

    What changes:

    1. Delegation is pre-configured, not ad-hoc. If the Level 1 Approver marks themselves as on leave, the system automatically routes new submissions to their designated deputy — no phone calls needed.

    2. Structured screening results are visible to the approver in a clear format — not buried in a free-text narrative.

    3. SLA indicator shows the approver if a report is approaching or past its target completion time.

    The three approval actions remain the same: Approve / Request For Information / Reject.

    For RFI, the approver selects a category (Missing Document / Unclear Conclusion / Insufficient Screening / Other) before entering their comment. This helps analyse why RFIs are happening and whether they can be prevented.

    Phase 7: Level 2 / MLRO Approval — With SAR Gate¶

    Role note: "Level 2 Approver," "MLRO" (Money Laundering Reporting Officer), and "Head of Compliance" refer to the same person in this process — the senior compliance role that performs the final approval and holds SAR-filing responsibility. This document uses these terms interchangeably; the system role is APPROVER_L2.

    What is new: Before the Level 2 Approver makes their decision, the system asks one additional question:

    "Based on your review of this report, is there any information that may require a Suspicious Activity Report (SAR)?"

    This is a mandatory step. If the answer is yes, the approval is paused and the Head of Compliance is alerted. The SAR process runs separately. If the answer is no, the approval proceeds normally.

    This gate ensures that the compliance head consciously considers their SAR obligation on every high-risk case — it cannot be overlooked.

    Phase 8: Completion — Automated and Monitored¶

    What changes:

    On final approval: - The system automatically generates the completed KYC report as a PDF - The requesting department receives an email with the report attached — no manual follow-up needed - The record is sealed (read-only) - A next review date is set automatically based on risk level: 12 months for High risk, 24 months for Medium risk, 36 months for Low risk (proposed periodic review intervals, aligned with general risk-based monitoring practice under FATF Recommendation 1; pending formal management sign-off)

    On rejection (at either Level 1 or Level 2): - The requesting department is notified automatically by email, with the stated rejection reason included - This directly closes GAP-10b from the As-Is process (V2), where a rejected KYC was never actively communicated back to the requestor

    Ongoing monitoring: - 60 days before a KYC is due for review: compliance officer notified - On the review date (if not yet renewed): manager notified - SLA breaches on open reports: flagged to manager daily

    Live KPI Dashboard — replaces "Madi, send me an export":

    The dashboard shows in real time: - Total KYCs completed this month / quarter / year - Average turnaround time - SLA compliance rate - Reports by risk level - Reports by contributor (team productivity) - Pending pipeline (what is in each stage right now) - Overdue cases

    What Changes for Each Person¶

    For Requesting Departments¶

    • Use a simple web form instead of sending emails
    • Upload documents in one place
    • Receive automatic confirmation and tracking
    • Get notified automatically when the KYC is complete

    • No more email triage — requests arrive in a structured queue

    • No double-entry between entity and report

    • Live dashboard — no data exports needed
    • Overdue cases flagged automatically
    • Team performance visible in real time
    • Periodic review schedule enforced by system, not memory

    KPI Note¶

    KPI Clock Start Point

    The turnaround time SLA is measured from docs_complete_date — the moment the compliance officer confirms all documents are present and correct.

    It is not measured from when the department first sent their email or submitted the form. The compliance team cannot be held accountable for delays in the department providing documentation.

    KYC Type SLA Target
    Simplified 5 business days
    AdHoc 10 business days
    Enhanced 20 business days

    All Workflow States¶

    State Who Can Act Available Actions
    DRAFT Contributor (owner only) Edit, Submit for Approval
    SUBMITTED / PENDING_L1 L1 Approver Approve, RFI, Reject
    RFI Contributor (owner only) Edit, Resubmit
    APPROVED_L1 System (auto-routes) —
    PENDING_L2 L2 / MLRO Mandatory SAR question, then Approve, RFI, or Reject
    FINAL_APPROVED Read-only View, Download PDF
    REJECTED Read-only View history

    Four-Eyes Principle

    A contributor cannot approve their own submission. This is enforced at the database level — the system checks that the approver's user ID differs from the contributor's user ID before allowing any approval action.
